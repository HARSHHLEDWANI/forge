# ADR 0007 — TLS via a Reverse Proxy (Caddy), Not in forge-server

Decision: forge-server never terminates TLS itself. A reverse proxy (Caddy, `deploy/Caddyfile`) sits in front of it, handles the TLS handshake and automatic Let's Encrypt certificate issuance/renewal, and forwards plain HTTP to forge-server over a private network (`deploy/docker-compose.prod.yml`) that never exposes forge-server's own port to the internet. Per explicit user direction, choosing between this and forge-server terminating TLS itself (e.g. embedding OpenSSL's TLS layer directly in `transport::HttpServer`).

## Reason

- **transport::HttpServer (Phase 12) is a deliberately minimal hand-rolled HTTP/1.1 server** — no keep-alive, single-threaded accept loop, exact-route matching (see `transport/http_server.hpp`'s own doc comment: "correct before fast," matching this project's stated style everywhere else, e.g. diff.hpp's single-hunk unified diff, ADR 0005/0006's "optimize once measured"). Certificate lifecycle — issuance, renewal before expiry, OCSP stapling, protocol/cipher negotiation, handling the ACME HTTP-01 challenge — is a substantial, security-sensitive subsystem with its own failure modes that has nothing to do with any of this project's own study goals (study-plan.md's learning targets are the git object model, HTTP itself, Postgres transactions/locking — not TLS/PKI). Building it from scratch here would be exactly the kind of premature, unjustified complexity this project's own rules elsewhere warn against.
- **Caddy already solves this correctly and is a single well-understood dependency**, not a library forge-server links against — it runs as its own container/process, with its own small, auditable config (`deploy/Caddyfile`), and does not touch this project's own source tree, build, or test suite at all. This keeps forge-server itself exactly as simple as Phase 12 left it.
- **A reverse proxy is the standard shape for this problem** — nginx, Caddy, or a managed load balancer in front of an application server that only speaks plain HTTP internally is how most real HTTP services are actually deployed, git-hosting platforms included.

## Consequence

- Running forge-server for real users requires a domain name that resolves to wherever it's deployed (Caddy's automatic certificate issuance needs that to succeed) — the one concrete external input this decision requires from whoever deploys it. See `deploy/README.md`.
- forge-server/forge-worker are deployed with **no published host port of their own** (`deploy/docker-compose.prod.yml`) — only the proxy is reachable from outside the deployment's private network. Local development (`docker-compose.yml`, this project's existing dev/test loop) is unaffected: it never talked to a real domain or TLS at all, and still doesn't.
- If forge-server is ever run directly, without the proxy in front of it (e.g. `docker run` by hand, or `./build/forge-server` locally), it still only serves plain HTTP — deploying it that way to the open internet without a proxy in front of it is a deployment mistake, not something forge-server can catch or warn about itself, the same way Postgres itself doesn't refuse to run without a TLS-terminating proxy in front of it either.
